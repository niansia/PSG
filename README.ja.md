PSG は Skill バンドルとローカル runtime のセットで、あなたのコーディングエージェントに 3 つのものを与えます。プロジェクトに対する永続的な記憶、変更してよい範囲の明確な境界、そして証拠にもとづく「完了」の定義です。Git と既存の Skill と並んで動作し、コーディングエージェントを置き換えることも、自分でソースコードを編集することもありません。

> あなたは普段どおりの言葉で依頼を続けるだけです。PSG は裏側で関連する文脈を取り出し、ロックされた決定とファイルを保護し、あなたが許可したチェックを実行し、レビューを実際に依頼したタスクの内側に保ち、古い証拠や裏づけのない証拠が「完了」と呼ばれることを防ぎます。

## インストール

インストールは一度だけです。このコマンドは runtime、完全な Skill バンドル、そして検出されたすべての Codex / Claude Code / Gemini CLI ホストへの MCP 統合をインストールします。

### Windows

```powershell
python -m pip install "psg-runtime[mcp] @ git+https://github.com/niansia/PSG.git@v1.1.2"; psg setup
```

### macOS / Linux

```bash
python3 -m pip install "psg-runtime[mcp] @ git+https://github.com/niansia/PSG.git@v1.1.2" && psg setup
```

そのうえで、Git プロジェクトごとに一度だけ有効化します。

```text
cd your-project
psg init
```

## 普段どおり使う

これで終わりです。あとはいつもどおりコーディングエージェントに話しかけてください。

```text
カートが空のときに親切なメッセージを表示して、終わったら検証までお願い。
```

PSG Skill が有効なとき、それはタスクを開いて追跡し、境界のある文脈を取り出し、実際の最終 diff を検証し、信頼できる検証結果を記録し、レビューをタスクの内側に保ち、ship gate を評価します。日常の作業でグラフを手動で操作する必要はありません。

日常的な操作はこれだけです。

```powershell
psg status       # PSG が有効か、何を把握しているかを確認
psg off          # 自動ガバナンスを一時的に停止
psg on           # 再び有効化
psg handoff      # 別のモデルや同僚に渡すレビューパックを作成
```

`psg off --global` と `psg on --global` は、初期化済みのすべてのプロジェクトで自動ガバナンスを停止・再開します。`psg update` は最新の安定版 `vX.Y.Z` リリースをインストールします。`psg update --channel dev` を明示的に選ばない限り、`main` を追いかけることはありません。`psg doctor` と `psg uninstall` は健全性の確認と削除を担当し、アンインストールしても各プロジェクトの永続的な `.psg/` 状態は保持されます。

### 2 つの利用モード

| モード | ホスト | 得られるもの |
| --- | --- | --- |
| **フル実行** | Codex · Claude Code · Gemini CLI | Skill に加えてローカル runtime と MCP サーバー。境界は**強制されます**。mutation ポリシーは実際の diff に対して検査され、検証は runtime が裏づけ、ship gate は機械が評価します。 |
| **レビュー／引き継ぎ** | ChatGPT · Claude · Gemini | `psg handoff` が書き出したレビューパックをアップロードします。レビュアーは同じ Task Contract と同じレビュー境界を読みます。 |

6 つすべてが 1 つの Task Contract を共有します。runtime による強制力を持つのは実行側だけです。チャット側のレビュアーは契約に「従う」のであって、契約を「執行する」わけではありません。

```powershell
psg handoff
```

レビューパックは `.psg/local/handoffs/<task>.md` に書き出されます。このパスは Git が無視します。これは重要です。ワークツリー内に書かれたレビューファイルは未追跡のプロジェクト変更となり、本来それが助けようとしていた ship gate 自体を塞いでしまうからです。`--output` で別の場所に書けますが、パスがワークツリー内にある場合は警告します。

`psg handoff` は厳密に読み取り専用です。タスクの状態を変えることも、イベントログに書き込むこともありません。

## なぜ PSG なのか

PSG が対象とするのは、エージェント支援の開発をいらだたしくする、ごく日常的な問題です。

- 新しい会話を始めるたびに同じリポジトリを読み直す。
- 重要な制約がセッションをまたぐと消えてしまう。
- 小さな依頼が無関係なファイルを書き換える。
- 「テストは通った」が、すでに変わってしまったコードを指している。
- 2 行の修正のレビューが、プロジェクトの問題点すべての一覧になって返ってくる。
- 繰り返されるレビューが、いったん受け入れたトレードオフを何度も蒸し返す。
- なぜその作業が完了とみなされたのか、誰も説明できない。

PSG はこれらを 5 つの具体的な保護機構に変えます。

| 必要なもの | PSG が提供するもの |
| --- | --- |
| 適切な文脈 | ファイル、Python シンボル、依存関係、タスク、決定、制約から構築される、トークン予算内のワーキングセット。 |
| 安全な変更 | 最終的な Git 状態に対するポリシー検査。ステージ済み・未ステージ・リネーム・削除・未追跡のファイルを含みます。 |
| 信頼できる証明 | 検証と受け入れの証拠が、正確なワークツリーとその実際の出所に結びついています。 |
| 境界のあるレビュー | どの指摘が**この**タスクに属し、どれが後続事項かを Task Contract が決めます。 |
| 本物の完了ライン | 範囲・チェック・受け入れ条件・レビュー・現在のコード・リスク要件がすべて一致したときにのみ `SHIPPABLE`。 |

## Task Boundary（タスク境界）

> **深刻度はタスクの範囲ではない。**
> **文脈が増えても権限は増えない。**
> **すべてのタスクには境界がある。すべてのレビューはその内側にとどまる。**
> **宇宙ではなく、そのタスクをレビューせよ。**

`blocker` が述べているのは「それがどれほど深刻か」であって、「それがあなたの依頼したタスクに属するか」ではありません。この 2 つを同じものとして扱うことこそ、1 行の修正が 1 週間の作業になる出発点です。

`psg task open` は正式な **Task Contract** を記録します。目標・文脈・mutation・範囲・レビュー・完了・リスクの各境界です。`review_record` はそのハッシュを検証するため、1 回のレビューがレビュー対象のタスク自体を広げることは決してできません。

### 文脈が増えても権限は増えない

タスクは **DRAFT** として開かれます。意図を述べ、範囲を要求しますが、書き込み権限はまったく持ちません。この状態でファイルを変更しようとすると、gate は契約が未封印だと告げます。

続く初回のローカライズがそれを **SEAL（封印）** します。PSG が導出した mutation 境界が `authorized_write`、`authorized_read_only`、`authorized_forbidden` となり、契約ハッシュが約束するのは**この組**です。

```text
ユーザーの依頼 → DRAFT（書き込み権限なし）
                    ↓  ローカライズ
                 SEALED → authorized_write がハッシュに入る
                    ↓
                 ビルダーはここで初めてファイルを変更できる
```

この区別は、簡単に見失われます。

| | 作業が進むと広がる | 権限として強制される |
| --- | ---: | ---: |
| **ワーキングセット** — 何を読むか | はい | いいえ |
| **Task Contract** — 何を変えてよいか | いいえ | はい |

文脈の拡張、再インデックス、再ルーティングは、いずれもタスクが**読む**範囲を広げられます。しかし、そのどれもがタスクの**書く**範囲を広げることはできません。封印後に見つかったファイルは文脈になるだけで、決して許可にはなりません。作業が本当に境界外のファイルを必要とするなら、それは新しいタスクです。このタスクへの静かな書き換えではありません。

境界が明示的な宣言ではなく、素の意図から導出された場合 —— ワイルドカードの書き込み範囲、高リスクのタスク、あるいは広がりすぎた書き込み集合 —— PSG は `requires_scope_approval` を立て、誰かが `psg task approve-scope` を実行するまで ship gate は止まったままになります。この承認は承認したハッシュに結びつくため、別の境界には引き継がれません。MCP からこのコマンドに到達することはできません。

すべての指摘は、タスクとの関係をちょうど 1 つ宣言しなければなりません。この集合は閉じています。

| 関係 | このタスクを止められるか |
| --- | --- |
| `caused_by_patch` | 可。証拠が必要 |
| `violates_acceptance` | 可。証拠が必要 |
| `violates_project_constraint` | 可。証拠が必要 |
| `pre_existing` | 不可 —— 後続事項 |
| `unrelated` | 不可 —— 後続事項 |
| `future_improvement` | 不可 —— 後続事項 |

指摘が現在のタスクを止めるのは、4 つの条件がすべて成り立つときだけです。open であること、`blocker` または `major` であること、関係が最初の 3 つのいずれかであること、そして証拠が十分であること。「十分」かどうかは runtime が検査するものであり、エージェントが主張するものではありません。

- 受け入れ違反は、実在する受け入れ条件 ID を挙げなければなりません。
- プロジェクト制約違反は、実在する Constraint、受理済みの Decision、ポリシー参照、または影響を受ける frozen／locked ノードを特定しなければなりません。
- caused-by-patch の指摘には、変更ノード、具体的な diff／runtime の証拠、または失敗した検証が必要です。

**エージェントは `blocks_current_task` を自分で設定できません。** エージェントが出すのは関係と証拠を伴う主張であり、その主張が阻害要因になるかどうかを導出するのは runtime です。後続事項は ship gate と handoff パックの中で完全に見えたままです。捨てられることはなく、ただタスクを人質に取らないだけです。レビュー回数と的を絞った修正サイクルは、上限 2 に固定されています。

## PSG オフ vs オン

本当に重要な問いは、実際のコーディングエージェントが PSG をオンにしたときにオフのときより良い仕事をするか、です。`benchmarks/agentic_ab.py` は、統制された実験にできる限り直接的な形でこれに答えます。

- 10 組のペアになった Python コーディングタスク。
- 両側で**同一の** Codex CLI、同一のモデル、同一の reasoning effort。
- 同じプロンプト、同じベースラインコミット、それぞれ独立したクリーンな Git worktree。
- 同一のサンドボックス権限と同一の MCP 設定。
- **OFF** = PSG はインストール済みだが無効。**ON** = PSG 有効。
- 成否は、エージェントが決して見ることのない**隠しテスト**で判定し、加えて既存の可視テストで退行を検出します。

タスク成功率が最重要の指標です。それを抜きにしたトークン数や実行時間の数字には意味がありません。

両側が知っている情報は完全に等しくなければならないため、ベンチマークには 2 つの明示的なモードがあります。

| モード | 対象ファイルを知らされる側 | 測定するもの |
| --- | --- | --- |
| `end_to_end` **（見出し）** | どちらにも知らせない | 素の依頼に対して PSG が役に立つか（ローカライズ込み） |
| `controlled_routing` | 両側に知らせる | ローカライズを一定にしたときのガバナンス自体の価値 |

ON 側にだけ変更箇所を教えることは、PSG に答えを渡すことに等しく、いかなる文脈の削減も無意味になります。したがってこのハーネスは決してそれをしません。

```powershell
python benchmarks/agentic_ab.py --output benchmarks/results/agentic-ab-latest.json --traces benchmarks/results/agentic-ab-traces
```

### 結果

> **この結果は差し替え済みであり、v1.1.2 を説明するものではありません。** データ自体は本物であり、都合の悪い証拠を消すことはラベルを貼るより悪いので残しています。現行版に対する主張として無効になる理由が 2 つあります。
>
> 1. **エージェントが読んだ PSG は、テスト対象の PSG と別物でした。** トレースを見ると Codex はグローバルにインストールされた `~/.codex/skills/psg/SKILL.md` を読んでおり、それは v1.1.1 以前のバンドルで、`context_expand` が書き込み範囲を広げられると告げていました。ランタイムは新しい規則を強制し、エージェントは古い規則に従っていたことになります。ハーネスは現在、インストール済み Skill のハッシュがこのチェックアウトと一致しない限り起動を拒否し、コミット・ランタイム版・Skill の SHA-256・CLI 版を毎回の結果に記録します。
> 2. **ローカライズはその後変更されました。** 当時は素の意図から 1〜8 ファイル（中央値 7）の書き込み権限が生まれ、10 タスク中 9 件で手動のスコープ承認が必要でした。v1.1.2 は検索候補と権限候補を分離し、同じ 10 個の意図に対して 10/10 で正しい対象ファイルだけを封印し、手動承認は不要になりました。この変更より前に測られたトークンやスコープの数値は、別のソフトウェアを説明しています。
>
> PSG が OFF 対 ON の主張を再び行う前に、再実行が必要です。以下の数値は測定どおりに、そして差し替え済みとして公開します。

10 ペア、`end_to_end` モード、Codex CLI・`gpt-5.5`・low reasoning effort、2026-09-01。
20 回の実行はすべて完走し、タイムアウトは 1 件もありませんでした。

| | PSG オフ | PSG オン |
| --- | ---: | ---: |
| **タスク成功** | 9 / 10 | **10 / 10** |
| 対象外ファイルの編集 | 10 | **2** |
| 退行 | 0 | 0 |
| 誤った `SHIPPABLE` | 0 | 0 |
| スコープ承認が必要 | — | 9 / 10 |
| 手動承認なしで封印 | — | 1 / 10 |
| 入力トークン | 1,984,624 | 3,543,483 |
| 出力トークン | 17,840 | 24,627 |
| 実行時間 | 763 秒 | 1,084 秒 |
| 報告されたコスト | CLI が提供せず | CLI が提供せず |

**対象外ファイルの編集**とは、単一の参照対象ファイル以外への変更すべてを指します。共有テストフィクスチャの編集はエージェントがタスクを終える通常のやり方なので、これは変更がどこに落ちたかの診断であって、それ自体がスコープ違反ではありません。「範囲外」と呼ばないのはそのためです。承認に関する 2 行を脚注ではなく本表に置いたのは、それが運用者の払うガードレールのコストだからです。

**PSG はエージェントをタスクの内側にとどめ、その代わりに入力トークンを 79% 多く使いました。** この文の両方が結果です。

範囲に対する効果が最も明確な信号です。OFF の 10 件の対象外ファイル編集は、すべて同じファイル `tests/test_existing.py` でした。10 のタスクすべてで、エージェントは自分の変更に合わせて既存の共有テストスイートを書き換えています。PSG オンでそれが起きたのは 2 回だけで、しかもその 2 回は、PSG 自身がそのテストファイルを書き込み境界に封印してしまった場合でした。

コスト差は誤差ではありません。入力トークン +79%、出力トークン +38%、実行時間 +42%。10 ペアの範囲は +14% から +198% です。

### この結果が示していないこと

- **10 ペアは小さなサンプルです。** これらは件数であり、統計的に有意な効果ではありません。
- **PSG 自身のローカライズは広い。** 封印された書き込み境界は 1〜8 ファイル（中央値 7）でした。10 件すべてが正しい対象を含んでいたので再現率は完璧ですが、適合率はそうではなく、10 件中 9 件が `requires_scope_approval` と記されました。これは「自分が導出した境界は黙って封印するには広すぎる」と PSG が正しく報告したものであり、同時に、テストファイルを編集した 2 件の ON タスクでそれが範囲に入ってしまった仕組みでもあります。
- **`unique_file_reads` は両条件を区別できませんでした** —— どちらも 4 です。これはコマンドイベントに現れたパスから推定した下界であり、このリポジトリでは情報になりません。
- リポジトリはハーネスが生成したものです。これは**統制されたペア比較の agentic ベンチマーク**であって実世界のベンチマークではなく、そう呼ぶことは誠実ではありません。

## プロジェクトに何が追加されるのか

`psg init` は小さな `.psg/` フォルダを作り、最初のインデックスを実行します。

```text
.psg/
├── config.yaml          # コミット可能なプロジェクト設定と実際の設定項目
├── policies.yaml        # コミット可能な mutation ポリシー
├── state/project.yaml   # コミット可能な決定・タスク・制約・証拠
└── local/               # 無視される SQLite、イベントログ、キャッシュ、生のチェック出力
```

YAML の状態はクローンやチームメンバー間で持ち運べます。保存するのは簡潔な証拠メタデータとハッシュであり、コマンド出力の全文ではありません。生の検証ログ、SQLite、イベントは無視される `.psg/local/` の下に留まります。ソースコードと Git が権威であり続けます。

起動時、PSG がガバナンス状態の変更を取り込むのは、それが前回の runtime エクスポートと一致するか、Git がクリーンだと報告する場合だけです。これは pull やコミット済み状態への checkout をカバーします。`project.yaml` や `config.yaml` でハッシュ不一致かつ dirty な場合は、設定で定義されたコマンドが実行される前に止められ、人が確認して明示的に受け入れるまで解除されません。

## ほかの Skill と共存します

PSG はガバナンス層であり、排他的なワークフローではありません。テスト Skill はテストを続けられ、設計 Skill は設計を続けられ、フレームワーク Skill は実装を続けられます。PSG はプロジェクトの文脈を供給し、それらの作業のまわりで受理済みの境界を強制します。

権威の順序は明示されています。ホストの規則とあなたの現在の指示が最優先で、受理済みのプロジェクト決定とリポジトリ規則が、タスク固有または一般的な Skill の好みより優先されます。ほかの Skill は変更を提案できますが、記録されたトリガーと承認なしに、frozen ノードを黙って解除したり、タスクの範囲を広げたり、必要な検証を弱めたり、受理済みの負債を蒸し返したりすることはできません。

正確な規則は[互換性契約](skills/psg/references/compatibility-contract.md)を参照してください。

## 仕組み

```text
通常の依頼
      │
      ▼
Task ──requires──▶ Requirement
 │                    │
 ├──targets────────▶ コードグラフ ◀──constrained-by── Decision / Constraint
 │                    │
 ├──bounded-by─────▶ Task Contract ──▶ レビュー境界 ──▶ 後続事項
 │                    │
 └──verified-by────▶ Verification
                           │
                           ▼
                    証拠にもとづく ship gate
```

- インデクサはファイル、Python シンボル、import、構造化された `psg-debt` 注記を対応づけます。
- ルーターは境界のあるワーキングセットを選び、確信度が低いときは一度だけ自動的に拡張します。
- ポリシーエンジンは実際の Git hunk を、ファイル・シンボル・決定・アーキテクチャ・範囲・依存の各規則に照らして検査します。
- 検証エンジンは MCP 経由では設定済みのチェック名しか受け付けず、生の出力はローカルに保持します。
- 信頼層はエージェントの主張、runtime が裏づけた証拠、明示的なユーザー承認を区別します。呼び出し側が自分の文字列を権威に格上げすることはできません。
- Task Contract は draft として開かれ、初回のローカライズで封印され、封印した権限をハッシュ化します。したがってルーティングもレビューも、書き込み可能な範囲を広げられません。
- 収束エンジンは Issue の状態と関係から阻害を導出し、runtime が数える予算を強制し、自己申告による高リスクの自己レビューを拒否します。
- 可搬状態層は `.psg/state/project.yaml` を通じて永続的なグラフ状態を同期します。ローカルの SQLite は必要に応じて再構築されます。

## 信頼モデル

PSG v1 は意図的に小さな信頼モデルを使います。

| ティア | 意味 | 通常の MCP から作れるか |
| --- | --- | ---: |
| `CLAIMED` | エージェント、レビュアーのラベル、外部ツールのラベル、提案、呼び出し側が与えた記述 | ✓ |
| `RUNTIME_ATTESTED` | PSG 自身が設定済みのチェックを実行した | 不可 |
| `USER_APPROVED` | 人が独立したローカル承認操作を行った | 不可 |
| `EXTERNAL_ATTESTED` | 将来の認証済み CI／コネクタアダプタ用に予約 | 不可 |

したがって MCP の `decision_record` と `debt_record` が作るのは提案です。frozen の解除、免除、負債の受理、ガバナンス状態の受理、高リスクの独立レビューは、通常の MCP からは自己承認できないよう意図的に設計されています。ローカル CLI が v1 における明示的な承認境界であり、Skill 契約はエージェントに対し、承認コマンドを自分で実行するのではなく提案を提示してユーザーを待つことを求めます。

同じ原則がレビューを支配します。エージェントは主張と証拠を提供し、何が阻害要因かを決めるのは runtime であってエージェントではありません。

同じ原則はタスクの記録のされ方も支配します。`task_open` は通常、依頼を仲介するエージェントを通じて実行されるため、生成される Task・Requirement・Constraint ノードは `user_explicit` ではなく `agent_interpreted_user_intent` と記録されます。これは実際に起きたことに対する正直なラベルであり、ユーザーが宣言したのではなくエージェントが導出した境界が、出荷前に明示的な承認を必要としうる理由でもあります。

## メカニクス回帰ベンチマーク

この合成ベンチマークは、生成された 38 ファイルの Python リポジトリ上で 12 個の連続タスクを実行します。各タスクは対象パスを与えられるため、測定しているのは**ローカライズ後**のルーティング効率です。

| 結果 | PSG |
| --- | ---: |
| `SHIPPABLE` に到達したタスク | **12 / 12** |
| 全ファイル基準に対するファイル読み取り | **89.69% 減** |
| 全ファイル基準に対する推定文脈トークン | **32.41% 減** |
| 未承認の frozen mutation | **阻止** |
| レビューが設定された予算で停止 | **はい** |

これは**メカニクス回帰ベンチマーク**です。公開されている全ファイル基準に対して、ルーティング・ポリシー・gate の機構が今も正しく動作することを示します。PSG が実際のコーディングエージェントをより効率的にするという証拠では**ありません**。その問いは上の OFF vs ON ベンチマークに属します。

```powershell
python benchmarks/sequential_benchmark.py --output benchmarks/results/latest.json
```

[生の結果](benchmarks/results/latest.json)と[ベンチマークの方法](benchmarks/README.md)を参照してください。

## 現時点の境界

PSG v1.1 は完成した、Python を第一とする研究用 MVP です。

- Python には豊富なシンボル抽出があります。それ以外のファイルはファイル単位のインデックスです。
- 2 つのベンチマークはいずれも生成されたリポジトリ上で動作し、その旨を明記しています。どちらも実世界のベンチマークではありません。
- PSG は作業を統治し評価します。実際のソース編集は依然としてコーディングエージェントが行います。
- スナップショットの復元は PSG のグラフ状態だけを復元します。Git をリセットすることも、ソースファイルを上書きすることもありません。
- `EXTERNAL_ATTESTED` は認証済みの CI／コネクタアダプタが登場するまで予約されたままです。`source="external_tool"` だけでは依然として主張にすぎません。
- handoff パックを読むチャット側のレビュアーは Task Contract に従いますが、それを強制することはできません。
- 封印された境界の拡張は意図的に自動化していません。v1 に task-amendment engine はありません。「もう 1 ファイル必要だ」への答えは「新しいタスクを開く」です。

次の意味のある一歩は、実際のリポジトリでのホールドアウト評価です。ガバナンス契約が証明される前に UI やベクトルデータベース、より多くの言語対応を足すことではありません。
